# Signal OS — Cross-Vertical Knowledge Graph

**Purpose**: This directory is the master cross-vertical knowledge graph for Signal OS. It encodes the microstructure knowledge (masking mechanisms, signal channels, signal-to-price translation) that the framework discovers across all asset classes, and connects it to the concrete detector code in each vertical.

It is **not** a muni-credit artifact — it spans real estate (rent_stabilization, art_donation_fraud, property_tax), buyside DD, public equities, muni credit, and any future vertical. The catalogs live here, at the repository root, precisely because every vertical reads and contributes to them.

## What's in here

| File | Purpose |
|---|---|
| `masking_mechanisms.json` | 22 mechanism entries (8 categories) with structural property, asset classes, validation depth, severity, signal-to-price impact, source citations |
| `signal_channels.json` | 73 channel entries (8 cadence types) with publisher, lag, market-watching depth, redundant siblings, asset classes |
| `knowledge_graph.json` | Composed graph: detectors × channels × mechanisms × asset classes (regenerated by build script) |
| `MASKING_MECHANISM_CATALOG.md` | Human-readable detail per mechanism with cross-asset clusters |
| `SIGNAL_CHANNEL_CATALOG.md` | Human-readable detail per channel with redundancy clusters |
| `build_knowledge_graph.py` | Re-runnable composition script. Scans every vertical's `detectors/` or `rules/` dir, joins to catalogs, writes graph |

## Why this lives at repo root

The knowledge graph is the spine of Signal OS's product. Every vertical:
- READS the catalogs to know which mechanisms/channels apply to its asset class
- WRITES findings back to the catalogs as it generates new microstructure knowledge

If the catalogs lived inside one vertical, other verticals would either duplicate them (bad) or have to reach across sibling-vertical paths (bad). Hence: repo root.

## How to use

**For vertical selection** — open `MASKING_MECHANISM_CATALOG.md`, find an `insurance_wrap` mechanism that's `MENTIONED_NOT_VALIDATED` (e.g., FHA Section 242), confirm a vertical hasn't probed it, and scope a validation pass on the analogous asset class. The catalog tells you the structural prediction; the validation test confirms or falsifies it.

**For detector development** — open `SIGNAL_CHANNEL_CATALOG.md`, look for channels that aren't read by any detector but have HIGH cadence × LOW market-watching depth (e.g., HCAI Cal-Mortgage Monthly Activity Report). Those are unscored signals.

**For new findings encoding** — every vertical scoping or validation pass should:
1. Add entries to `masking_mechanisms.json` for any new structural mechanism discovered
2. Add entries to `signal_channels.json` for any new data source used
3. Re-run `build_knowledge_graph.py` to update `knowledge_graph.json`
4. Update the relevant `*_CATALOG.md` surface files

Don't generate standalone prose memos with one-off findings — they become unfindable. Update the structured catalogs.

## Anti-patterns to watch

- **Generating prose memos for one-off findings.** Update the catalogs instead.
- **Treating verticals as alpha hunts where failed alpha = kill the vertical.** Every failed alpha test is encoded microstructure knowledge (it confirms the signal is market-efficient).
- **Per-vertical catalog drift.** All verticals share these JSONs. If a vertical needs a local extension, propose an addition to the global schema, not a parallel file.
